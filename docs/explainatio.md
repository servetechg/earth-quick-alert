AI Risk Assessment - Requirement Specification
1. Context & Core Logic
Data Source: All event data must be fetched from the database model UnifiedEvent.
Dynamic Data Scoping: You will only display historical/past data for categories that currently have an active incident. For example, if there is a current earthquake event, the report will display active earthquake data and fetch its past historical data.
Empty States: If no active incident exists for a specific hazard category (e.g., Flood), do not show any information for that category. It should be excluded from the bar chart (incident distribution) and the Historical Context section completely.
2. Features
Overall Threat Level
Logic: Calculate the average severity of all current events. Whatever current data is received across all categories, derive the average of the severity field and display it here.
Active Incidents
Logic: Display the total number of current active events received from the realtime API.
Breakdown: Categorize the active incidents count into two variables: Major and Minor. The differentiation between major and minor must be decided entirely based on the severity fielkd.
AI Confidence & Population at Risk
Logic: Leave as is for now. (Deferred for future development).
Incident Distribution
Logic: This is a dynamic field displayed as a bar chart.
Display: Show the event score or count grouped by each hazardous category (e.g., Marine, Flood) natively fetched from the active realtime API (current data) mimicking the provided visual design.
Severity Levels
Logic: Dynamically display only the severity levels which are currently present in the active events data.
Display format: There are up to 4 potential dynamic boxes corresponding to the 4 severity possibilities in the database (severity field).
Content Generation (AI Summarization):
Under each displayed severity level, show a summary of each hazardous category grouped under that severity.
Example: If the severity level is "High", fetch all current events categorized as "High". Group them by hazard type (e.g., Flood). Pass all event data, properties, and relevant fields from the DB to the OpenAI API to generate a summarized report. Report generation repeats per category under that severity level.
Data Requirement: Make sure all key details, exact numbers, and statistics are explicitly mentioned in the generated summary.
Historical Context & Mitigation Strategy
Logic: Data displayed here is dynamically based on current data. Create a distinct tab for each active hazard category. If a category is not actively occurring, its tab must be hidden.
Fields to Display Per Category Tab:
Matched Event: The similar recent active event generated by AI using data from the DB current API. Clearly define the event name, date, time, key statistics, numbers, and other details.
Past Damages & Losses (What it cost last time): Capture current event details/properties (e.g., "magnitude" for earthquakes). Utilize these specific fields to extract at least three statistically similar events from the past data available in the DB. Pass these records to the OpenAI API. The summary must contain event names, dates, times, fatalities, injuries, property/crop damage metadata, exact numbers, and loss figures.
Past Procedures (Mitigation steps taken then): Extract three similar past events using the same correlation logic above. Pass these to the OpenAI API to generate a summary. The summary must contain event names, dates, times, statistics, exact numbers, federal aid payouts/damage costs, and details regarding past strategies and initiatives implemented.
Current Procedures (From live ingest for this category): Fetch the live API data for the category. Analyze the properties payload for the best fields, and pass that data to the OpenAI API. The AI output should describe the event names, dates, times, statistics, exact numbers, federal aid expectations, and other relevant details responding to the live emergency.
Future Preventative Measures (AI-recommended long-term plan): By analyzing both the "Past Procedures" and "Current Procedures", the AI must formulate long-term initiatives and strategies. The generated solutions must be realistic, highly detailed, expert-level (not general or basic), and fit to be presented to high-level executives to take structural measures.
Strategic Recommendations (Prioritized action plan): Translate the previously generated "Future Preventative Measures" into a detailed, step-by-step action plan. The plan must categorize tasks using the statuses: Urgent, Immediate, and Standard.
3. Technical Guidelines & Constraints
Latency Optimization (Progressive Loading): Do not wait for AI to finish generating all summaries before rendering the page. Non-AI data (raw database numbers) should be displayed immediately to reduce perceived latency.
AI Isolation: Within the "Historical Context & Mitigation Strategy" section, you must call the OpenAI API separately for each category to ensure the AI does not hallucinate or mix up data points between different hazards. Implement necessary asynchronous strategies to optimize this loading time.
Handling Missing Data: If no historically similar data is found in the database—preventing the formulation of "Past Damages & Losses" and "Past Procedures"—gracefully degrade the UI by displaying a suitable, relevant message for the user instead of returning an error summary.
Data Fetching: To fetch realtime api data, you are authorized to fetch all categories in a single request or in chunks; strictly utilize whichever method proves most effective at reducing fetch latency.
